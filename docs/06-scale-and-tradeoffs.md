## 0. 一句话结论

> 以下数字除特别说明外，均取自 **REMOTE_HOST chip4 真引擎**上的 A/B（`docs/04` C1–C3，
> 两侧同一镜像、同一引擎、只换前端）。**mock engine 的数字只作乐观上界**（见 §3.1）。

1. **换 Rust 前端省的是 CPU，不是延迟。** 在真引擎上（ISL=1k/OSL=128/c=1），
   前端每请求吃 **10.31 ms CPU**，而端到端是 **689 ms**——
   前端占比 **1.5%**；两侧 TTFT 只差 **6.8 ms**（83.7 vs 90.5 ms）。
   ⇒ **前端从来不是延迟瓶颈**（结论与装置无关：本机 x86 上差距更小）。
2. **但「省多少 CPU」是实打实的：Rust 前端 CPU 是 Python 的 0.23–0.37 倍**
   （C1 0.225 / C2 0.315 / C3 0.368），**在高并发下从「噪声」变成「规划项」**：
   Python 前端在 C2（c=64）占到**服务端总 CPU 的 17.03%**，Rust 只占 6.02%。
3. **拐点在「核预算」轴上，而且比 mock engine 给出的更早到来**：
   按两点法解出的**边际成本**（同负载、只改请求数，已扣掉空转），
   **单核 Rust 前端 ≈171 req/s、Python ≈26 req/s**——Python 要 **6.5 倍**的核。
   ⇒ **单核前端只能撑上百 req/s 量级**（不是 mock engine 暗示的上千）。
   顺带：**Rust 前端闲着的时候也更省**（空转 0.57% vs 0.90% 单核）。
4. **前端成本的形状由引擎的 tick 粒度决定**，不是一个静态答案：
   密集 tick（mock）⇒ 拷贝/分配主导、可批量摊销；稀疏 tick（真引擎，4.8 ms/tick）
   ⇒ **唤醒/轮询/收包**主导、按 tick 计费（拷贝 15.2%→2.97%、分配 14.2%→4.9%、
   tokio 分发改 13.9%→21.9%，`docs/02`）。**这也是为什么 mock engine 的数字
   不能用来做容量规划**。
5. **最值得动的一刀不在「换前端」，在 Rust 前端内部的搬运与唤醒**：
   真引擎下每输出 token 的边际成本仍以跨段开销为主（§3.1、`docs/02` §8.3），
   其中 **P4 的 PCRE2 预分词在 ISL=8k 时占前端 on-CPU 的 41.71%**——
   这是换语言换不掉的、Rust 侧自己该优化的部分。

## 2. Q4 的第一问：延迟轴上有没有拐点？

**没有。** 前端占端到端的比例 = F / (F + TTFT + OSL × TPOT)：

<!-- 由 harness/scale/extrapolate.py 生成，可一键复算：
     ./harness/scale/extrapolate.py --fe-ms 10.31 --isl 1024 --osl 128
     ./harness/scale/extrapolate.py --fe-ms 20.00 --isl 8192 --osl 16 -->

**引擎每请求时间 = prefill TTFT + OSL × TPOT**，其中 TTFT 由 C1/C3 两点拟合
（`TTFT ≈ 45.2 ms + 37.6 µs × ISL`，两点完全拟合）。
**prefill 必须计入**——长 prompt 时它才是引擎侧主项（8k prefill ≈ 308 ms，
而 OSL=16 的 decode 只有 76 ms）。

### 表 A1：ISL=1k / OSL=128（前端 10.31 ms，`docs/04` C1）

| 引擎 decode 速度 | prefill | decode | 引擎合计 | **前端占比** |
|---|---:|---:|---:|---:|
| x86 纯 CPU（实测）TPOT 245 ms | 83.7 ms | 31,360 ms | 31,444 ms | **0.033%【推断】** |
| **REMOTE_HOST chip4（实测）TPOT 4.7 ms** | 83.7 ms | 604.9 ms | **688.7 ms** | **1.475%【推断】** |
| 前项目 engine-core 口径 TPOT 4.9 ms | 83.7 ms | 629.1 ms | 712.9 ms | **1.426%【推断】** |
| 假想：小模型加速卡 TPOT 1 ms | 83.7 ms | 128.0 ms | 211.7 ms | **4.643%【推断】** |
| 假想：极快 decode TPOT 0.2 ms | 83.7 ms | 25.6 ms | 109.3 ms | **8.617%【推断】** |

▶ 第一行（**实测档**）的 688.7 ms 与 C1 实测端到端量级一致 ⇒ 模型可信。

### 表 A2：ISL=8k / OSL=16（前端 20.00 ms，`docs/04` C3）

| 引擎 decode 速度 | prefill | decode | 引擎合计 | **前端占比** |
|---|---:|---:|---:|---:|
| x86 纯 CPU（实测）TPOT 245 ms | 353.5 ms | 3,920 ms | 4,273 ms | **0.466%【推断】** |
| **REMOTE_HOST chip4（实测）TPOT 4.7 ms** | 353.5 ms | 75.6 ms | **429.1 ms** | **4.454%【推断】** |
| 假想：小模型加速卡 TPOT 1 ms | 353.5 ms | 16.0 ms | 369.5 ms | **5.135%【推断】** |
| 假想：极快 decode TPOT 0.2 ms | 353.5 ms | 3.2 ms | 356.7 ms | **5.308%【推断】** |

**读法（两条都与直觉相反，但都有实测支撑）**：

* **表 A2 里「引擎越快，前端占比反而越高」的趋势消失了**——因为 prefill（353.5 ms）
  主导了引擎时间：把 decode 从 75.6 ms 压到 3.2 ms，前端占比只从 4.45% 升到 5.31%。
  ⇒ **长 prompt 场景下，前端占比由 prefill 决定，与 decode 速度几乎无关。**
* 因此**本计划找到的最高前端占比只有 ≈8.6%**（表 A1 的「极快 decode」假想档），
  而非早期草案里估的 23–29%——那个估计**漏掉了 prefill**，已修正。
* ⚠️ 除标注「实测」的两档外，其余引擎速度均为**假想值**；前端列来自真引擎实测，
  外推时假设「前端成本不随引擎变化」——**该假设未验证**（见 §3.1）。

> ⚠️ **方法学提醒：表 A 用的是「前端 CPU 时间」，它不是「关键路径时间」。**
> 前端处理与引擎处理**有重叠**：前端把请求交给引擎后就空闲等 tick，
> decode 期的输出处理也可能与引擎下一 tick 并行。
> 用 `docs/04` 的 C1 实测可以量化这个差别：
>
> | C1（ISL=1k/OSL=128/c=1） | Rust | Python | 差 |
> |---|---:|---:|---:|
> | 前端 CPU | 10.31 ms | 45.94 ms | **35.63 ms** |
> | 其中体现在 TTFT（首 token 前，串联） | 83.7 ms | 90.5 ms | 6.80 ms |
> | 其中体现在 TPOT（decode 期，部分并行） | 4.726 ms/tok | 4.820 ms/tok | 12.03 ms |
> | **落回关键路径的合计** | — | — | **18.83 ms（53%）** |
>
> ⇒ **前端 CPU 的差额只有约一半变成端到端延迟的差额**；另一半与引擎并行。
> 所以表 A 的数字应读作**上界**，Q3 的「省多少延迟」要按**关键路径**（≈53%）打折。
> 这也解释了为什么两侧 TTFT 只差 6.8 ms，而 CPU 差了 35.6 ms。

## 3. Q4 的第二问：容量轴上拐点在哪？

这一问才有实际意义。前端 CPU 是**按请求计费**的固定成本，引擎是**按 token 计费**的
稀缺资源；当请求率很高时，前端的核占用会变成可观的成本项。

### 表 B：前端要吃掉几个核（ISL=1k / OSL=128，Rust 前端实测模型；【推断】）

⚠️ **两个必须用对的量：① 用真引擎实测，不用 mock engine（见 §3.1，差 5.2×）；
② 用「边际成本」，不用「含空转的均值」。**

后者是 `docs/04` §2 的两点法给出的（同负载、只改请求数，解出空转速率与边际成本）：

| 臂（ISL=1k / OSL=128 / c=1） | 含空转的均值 | **边际成本** | 空转速率 |
|---|---:|---:|---:|
| **Rust** | 10.31 ms/请求 | **5.86 ms/请求**（±25%） | 0.57% 单核 |
| **Python** | 45.94 ms/请求 | **37.83 ms/请求**（±2%） | 0.90% 单核 |
| **比值** | 0.225 | **0.155（省 6.5×）** | — |

⇒ **容量规划要用边际成本那一列**：均值里含了「窗口里前端空转」的摊薄，
而空转**不随请求数增长**，在请求率上升时会被摊没。

### 表 B：前端要吃掉几个核（ISL=1k / OSL=128，**边际成本**口径；【推断】）

| 目标请求率 | Rust 前端核数 | Python 前端核数 | 差值 |
|---:|---:|---:|---:|
| 10 req/s | 0.06 核 | 0.38 核 | 0.32 核 |
| 50 req/s | 0.29 核 | 1.89 核 | **1.60 核** |
| 100 req/s | 0.59 核 | 3.78 核 | **3.20 核** |
| 171 req/s | **1.00 核** | 6.47 核 | 5.47 核 |
| 500 req/s | 2.93 核 | 18.9 核 | **16.0 核** |

> 「核数 = 请求率 × 边际每请求前端 CPU」。**单核 Rust 前端 ≈ 171 req/s
> （边际口径）、单核 Python 前端 ≈ 26 req/s。**
> ⚠️ 若用含空转的均值（10.31 / 45.94 ms），同样算法会给出 97 / 22 req/s——
> **那是低请求率场景下的值**（空转摊不掉），两者都真实，取决于你在哪一段。

**拐点的正确表述（据实测改写）**：

> 当「每秒请求数 × 每请求前端 CPU」接近「你愿意分配给前端的核数」时，
> 前端语言的选择才开始值钱。
> 以真引擎的**边际成本**计，**单核 Rust 前端 ≈171 req/s、Python ≈26 req/s**（低并发负载）；
> 高并发（c=64）下两者每请求成本都更低（Rust 4.84 / Python 15.35 ms，含空转），
> 因为一次 tick 产出更多 token、每 tick 固定开销被摊薄。
> ⇒ **在「每核要撑上百 req/s」的场景里，前端已经从噪声变成了规划项**，
> 而同口径下 Python 需要 **6.5 倍的核**（边际口径）。
> ⚠️ 这些数字比 mock engine 给出的 ≈1100 req/s 低一个数量级——原因见 §3.1。

### 3.0 顺带一个结论：空转本身也是 Rust 前端的优势

两点法解出**空转速率**：Rust **0.57%** 单核 vs Python **0.90%** 单核。
⇒ Rust 前端不仅处理更便宜，**闲着的时候也更省**（尽管它的线程数更多：
77 vs 51）。在「大量空闲连接、偶发请求」的服务形态里，这一项会独立累积。
（⚠️ 单次测量，未评估轮间漂移。）

### 3.0b 反向验证：核数（CPU 拓扑宽度）**不是**瓶颈

`docs/04` 的 C5 做了直接对照：把服务容器的 cpuset 从 **40 核砍到 16 核**（−60%），
同负载下 Rust 前端成本只 +6.8%、Python 只 +2.4%，吞吐变化 −3.7%/+0.9%（都在单轮噪声内）。

* 原因：**前端远没吃满核**——C2（15.5 req/s）时 Rust 前端只占 **0.35 个核**、
  Python 占 **1.13 个核**；C5（7 req/s）时只有 0.17 / 0.49 个核。
* ⇒ 这反过来印证了 §3 的结论：**在本装置的请求率量级上，前端是"零头"**；
  只有当请求率再上一个数量级（§3 表 B 的 500+ req/s 档）时，核数才会成为约束。
  **"核数不是瓶颈"与"前端该省核"并不矛盾**：前者说的是当前装置，后者说的是规模。

### 3.1 ⚠️ 为什么不能用 mock engine 的数字做容量规划

| 装置 | 每请求前端 CPU | 每 token 折算 | 成本构成 |
|---|---:|---:|---|
| x86 + mock engine（`docs/02` B1） | **1.83 ms** | 14.3 µs | 拷贝 15.2% + 分配 14.2%（**批量处理**） |
| REMOTE_HOST + 真引擎（`docs/02` A1/A5） | **9.53 ms** | 74.5 µs | 拷贝 **2.97%** + 分配 **4.9%**，tokio 分发 **21.9%**（**按 tick 计费**） |

mock engine 的 tick 极密（B 线实测 chunk=32 时成本 −72%）⇒ 前端能一次醒来处理多个 token；
真引擎每 tick 只回 1 个 token、间隔 ≈4.8 ms ⇒ 前端每次唤醒只处理 1 个 token。
**这是同一条代码路径在不同引擎节奏下的两种成本形状**，不是矛盾。

⇒ **容量规划必须用真引擎数字**；mock engine 的数字只能作为「前端能力的乐观上界」。

## 4. ISL 维度：Rust 前端在哪里优势最大

`docs/05` 的分段对照（同输入同尺寸，两侧 sha256 相同）：

| 段 | Rust/Python @1k | Rust/Python @8k | 趋势 |
|---|---:|---:|---|
| P2 JSON 反序列化 | 0.56 | **0.36** | **ISL 越大越划算** |
| P3 模板渲染 | 0.59 | 0.47 | 略随 ISL 变好 |
| P6 msgpack 编码 | **1.30** | **1.50** | ⚠️ **Rust 反而更慢，且随 ISL 恶化** |
| P7 msgpack 解码 | 0.41 | 0.40 | 稳定 |
| 四段合计 | 0.58 | 0.51 | — |

再叠加 B 线的线上占比：**P4 是唯一被 ISL 放大的业务段**
（49.2 → 412.8 µs，斜率 50.9 ns/输入 token，其中 PCRE2 预分词 22.1 ns/token）。
Rust 侧 P4 的绝对值不低（ISL=8k 时占前端 on-CPU 的 **41.71%**），
但它**在 Python 侧同样存在**，且 Python 侧有解释器派发开销叠加。

⇒ **长 prompt 场景是 Rust 前端最划算的场景**（P2 优势随 ISL 拉大 + P4 占比高）。
⚠️ 但 P4 的 **Rust vs Python 同口径对照本计划未做**（`docs/05` 的 D5 只引用了
tokenizer 项目的 Python 侧结论，跨装置不可比）——这是本文的一条**未测项**。

### 4.1 ⚠️ 一个方向与预期相反的实测结果（已用受控点排除混淆）

用 `docs/04` 的**受控点 I8k**（ISL=8k / **OSL=128** / c=1，与 C1 只差 ISL）：

| | ISL | OSL | Rust 前端 | Python 前端 | 比值 |
|---|---:|---:|---:|---:|---:|
| C1 | 1 024 | 128 | 10.31 ms | 45.94 ms | **0.225** |
| **I8k（受控）** | 8 192 | **128** | 26.88 ms | 85.63 ms | **0.314** |
| C3（两轴同变） | 8 192 | 16 | 20.00 ms | 54.38 ms | 0.368 |

⇒ **固定 OSL、只把 ISL 从 1k 拉到 8k，比值仍从 0.225 升到 0.314。**
所以「Rust 在长 prompt 上优势更大」这个**来自分段微基准的预期，在端到端真实负载上不成立**——
方向是真实的，**不是两轴同变造成的假象**。

**机制（C 线标注「有受控证据、待验证」）**：长 prompt 时前端**等 prefill 的时间更久**
（8k prefill ≈308 ms vs 1k 的 84 ms），而唤醒类开销**按时间累积**；
同时 Python 侧的成本增长斜率更平（它本来就有更多"大块"开销在长输入上被摊薄）。

**完整的比值地图**（把 `docs/04` 全部点按"变化的轴"排开）：

| 变化的轴 | 点 | 比值 | 方向 |
|---|---|---:|---|
| 基准 | C1（1k/128/c=1） | 0.225 | — |
| **OSL ↑**（128 → 512） | C4 | **0.224** | **无影响** |
| **ISL ↑**（1k → 8k，OSL 固定 128） | I8k（受控） | **0.314** | 变差 |
| **并发 ↑**（c=1 → 8） | C5w | 0.349 | 变差 |
| **并发 ↑**（c=8 → 64） | C2 | 0.316 | 略回落 |
| **核数 ↓**（40 → 16 核） | C5n | 0.364 | 与 C5w 同档（噪声内） |
| 两轴同变（ISL↑ + OSL↓） | C3 | 0.368 | 与 I8k 同档 |

⇒ **让比值变差的轴是「ISL」与「并发」，不是「OSL」。** 这条地图把 §4.1 的结论
从「一个反直觉的点」扩展成「一个有结构的规律」，也解释了为什么 C3（0.368）
只比受控的 I8k（0.314）再差一点：多出来的那点来自 OSL 变小、固定开销更难摊。
⚠️ 除 C1（3 轮）外都是单轮，**方向可信、数值不要当三位有效数字用**。

⚠️ **与本项目分段结论的关系**：`docs/05` 的微基准显示 **P2（JSON 解析）的
Rust/Python 优势随 ISL 从 0.56 拉大到 0.36**——但那只是**四段之一**，
而端到端比值被**唤醒/调度那部分**主导（真引擎下 tokio 分发占 21.9%，见 §3.1）。
⇒ **「某一段更划算」不等于「整个前端更划算」**，这是本项目给"微基准不能外推"的一个实例。

⚠️ 本节的 I8k 是**单轮**（n=16），且比值 0.314 与 C3 的 0.368 之间还差着 OSL 的影响；
**「ISL 与 OSL 各自的独立效应」仍未分离**（未测项，见 §7）。

## 5. 反过来说：Rust 前端自己的账

本项目最有行动价值的发现，不在「Rust vs Python」，而在**Rust 前端内部**——
而且**「内部哪里贵」取决于引擎 tick 粒度**（同一份代码，两种装置给出两套答案）：

| 桶 | x86 + mock engine（`docs/02` B1） | **REMOTE_HOST + 真引擎（`docs/02` A1/A5）** |
|---|---:|---:|
| X-copy 拷贝/比较 | **15.20%** | **2.97%** |
| X-alloc 分配（mimalloc 家族） | 14.18% | **4.9%** |
| X-runtime 分发/调度（tokio） | 13.90% | **21.9%** |
| P4 分词（含 PCRE2 预分词） | 6.57%（ISL=8k 时 **41.71%**） | 同机口径见 `docs/02` a3 节 |
| 内核态（仅全栈采样可见） | — （`:u` 采样看不到） | **32.9%** |

* **密集 tick（mock）**：前端能批量处理 ⇒ **拷贝/分配主导**（跨段三桶 43.28%，
  而 P1–P10 业务段只有 32.65%），每输出 token 4.22 µs 里 55% 是搬运而非语义。
* **稀疏 tick（真引擎，4.8 ms/tick）**：每 tick 只回 1 token、无法批量
  ⇒ **唤醒/轮询/收包主导**（tokio 分发升到 21.9%），且**近三分之一时间在内核里**。

⇒ 若要继续降低前端成本，**下一刀依场景而定**：

1. **长 prompt（ISL≥8k）**：砍 **P4 的 PCRE2 预分词**——它在 ISL=8k 时占前端
   on-CPU 的 **41.71%**，`docs/05` D6 独立证实 fastokens 的预分词正则占 encode 的
   71%（1k）/ 88.7%（8k）。**这是 Rust 侧自己该优化、且与语言替换无关的部分。**
2. **稀疏 tick 的真引擎场景**：砍**每 tick 的唤醒与系统调用**——真引擎下
   tokio 分发 21.9% + 内核态 32.9%，而 R9 的 `sys_enter_write` 达 **208 次/请求**
   （OSL=128，即每 SSE chunk 一到两次 write）。**减少 write 次数（攒批/更宽的 chunk）
   比优化拷贝更对症。**
3. **密集 tick / 高吞吐场景**：砍**逐 token 的拷贝/分配**（mock 口径下
   X-copy + X-alloc 在 OSL 上的斜率 910 + 644 ns/token）。
4. **P6 msgpack 编码**是唯一 Rust 输给 Python 的段（1.30×/1.50×，随 ISL 恶化）——
   量级不大，但方向确定、值得记一笔。

⚠️ 以上是**观测结论**，不含任何优化实现——本计划按 `plan/EXECUTION.md §9`
**不改 `vllm-rs` 代码**，这些是交给上游的线索。

## 6. 选型建议（把话说圆）

### 6.1 什么时候**不值得**换

* 你的瓶颈是**端到端延迟、且 prompt 短**：C1（ISL=1k）上前端只占端到端 **1.5%**，
  两侧 TTFT 只差 **6.8 ms**（689 ms 端到端的 1%）。**短 prompt 上换前端感觉不到。**
* 你的请求率**远低于几百 req/s**：单核前端就能撑住，省下来的核不构成成本项。
* 你的负载是**短 prompt**：ISL 是前端成本的主要驱动（§1.1），短 prompt 下两边都便宜。

### 6.2 什么时候**值得**换

* **高并发（c≥64）**：Python 前端占到服务端 CPU 的 **17.03%**（C2），Rust 只占 6.02%
  ——**这是本项目最有力的「值得换」证据**。
* **长 prompt（≥8k）且你在意 TTFT**：`docs/04` 的受控点 I8k 实测
  **TTFT 差 −82.8 ms**（两侧引擎相同、只换前端）——**这是本项目唯一测到的、
  幅度足够让用户感知的延迟收益**。它比 C1 的 6.8 ms 大一个数量级，
  因为长 prompt 的前端处理（P2/P4）与 prefill 是**串联**的。
  ⚠️ 但注意 §4.1：长 prompt 的**CPU 比值**反而变差（0.225→0.314），
  即**「延迟收益更大」与「CPU 相对优势更小」是同时成立的**，别把两件事混为一谈。
* **高请求率或核预算紧张**：单核 Rust 前端 ≈171 req/s（边际口径），Python 需 **6.5 倍**核；
  含空转口径下则是 97 vs 22 req/s（低请求率分段）。
* **同一台机器上还要跑别的东西**：前端省下的核可以被引擎或其它服务用掉。
* **需要前端承担额外工作**（多模态预处理、结构化输出、复杂 parser）：
  Rust 侧这些是**编译后的原生代码**，不像 Python 侧要走解释器派发。

### 6.3 ⚠️ 一条不能反着用的结论

上面的「值得换」**全部是 CPU/容量口径**。若有人拿它去主张「换 Rust 前端能降延迟」，
那是**误用**：C1 的端到端差异只有 1%，且 TTFT 的 6.8 ms 差里还含排队与 prefill，
**没有做分解实验**（未测项）。**换前端的收益在核预算上，不在延迟上。**

### 6.4 一句话

> **换 Rust 前端不是「快」的投资，是「每请求省几百 µs CPU」的投资。**
> 它不会让端到端变快（前端从来不是瓶颈），但在**每秒上千请求**的规模上，
> 它把前端从「不可忽略的核开销」降到「更小的核开销」；
> 而在**长 prompt** 场景，它的逐段优势最明显。
> 真正的性能红利，可能还在 Rust 前端**内部**那 55% 的拷贝/分配/调度上。

## 7. 未测与限制（引用本文前必读）

| 项 | 状态 | 原因 |
|---|---|---|
| 表 A/B 的引擎时间轴 | **推断** | 引擎不是本计划的分析对象；「x86 纯 CPU」与「REMOTE_HOST chip4」两档是实测，其余为假想档 |
| prefill TTFT 模型（45.2 ms + 37.6 µs×ISL） | **两点拟合** | 由 C1/C3 解出、无第三点校验；且 C1/C3 的 OSL 不同（128 vs 16），非受控 |
| 「前端成本不随引擎变化」假设 | **未验证** | 前端模型采自真引擎；外推到其它引擎速度时假设其形状不变 |
| **ISL / 并发 对「Rust/Python 比值」的独立效应** | ✅ **已测** | 受控点 I8k（固定 OSL、只变 ISL）与 C5/C2（只变并发）联合给出「比值地图」（§4.1）：**ISL↑ 与 并发↑ 让比值变差，OSL↑ 无影响** |
| OSL 的独立效应 | **两点** | C1（OSL=128）与 C4（OSL=512）比值几乎相同（0.225/0.224），支持「OSL 不影响比值」；但只有两点 |
| 长 prompt TTFT 收益（−82.8 ms）的机制分解 | **未测** | 未做「前端处理 vs 排队」的分解实验；I8k 也是单轮 n=16 |
| 前端 CPU 中「关键路径 vs 并行」的精确拆分 | **部分** | 用 C1 的 TTFT+TPOT 差分估得 ≈53% 落关键路径（§2），但 TTFT 含排队与 prefill，未做分解实验 |
| C2/C3/C4/C5 的重复次数 | **单轮**（C1 是 3 轮） | 机时受 chip4 与其它线共享所限；噪声未评估 |
| P4 分词的同口径 Rust vs Python | **未测** | `docs/05` D5 直接引用 tokenizer 项目结论，跨装置不可比 |
| 跨段桶（mock 43.28% / 真引擎 tokio 21.9%）到具体代码位置的分解 | **未测** | 需要插桩/eBPF，超出「不侵入观测」的范围 |

| 多模态 / 结构化输出 / LoRA 路径 | **未测** | 按计划不覆盖 |
