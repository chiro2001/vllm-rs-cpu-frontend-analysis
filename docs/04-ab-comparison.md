# 04 · 同负载 A/B：Rust 前端 vs Python 前端

> C 线（★04）主交付物。回答 **Q3**（换 Rust 前端值不值）与 **Q4**（拐点在哪）。
> 方法学与公平性论证见 [`docs/ab-design.md`](ab-design.md)；本文只给**数字与结论**。
>
> **装置**：REMOTE_HOST，Ascend 910 **chip4（`/dev/davinci4`）**，Kunpeng 920B。
> **两侧**：同一镜像 `quay.nju.edu.cn/ascend/vllm-ascend:v0.26.0rc1-a3-openeuler`、
> 同一份 vLLM 0.26.0 引擎（源码 commit `568afb3a`，与计划锁定值一致）、同一张卡、
> 同一模型 `Qwen3.5-0.8B`、同一压测客户端（镜像内 `vllm bench serve`，独立容器、绑核 200-201）。
> **唯一变量**：`VLLM_USE_RUST_FRONTEND`（Rust 侧 =1 且指向 `vllm-rs`，Python 侧 =0）。

---

## 0. 一分钟结论

1. **前端 CPU：Rust 是 Python 的 0.22–0.37 倍。** 单流（C1，3 次重复）稳定在
   **0.225**；并发 c=64（C2）是 **0.316**；长 prompt（C3/I8k）是 **0.31–0.37**。
2. **扣掉空转后的「边际成本」差距更大**：两点法（§2）给出 Rust **5.86 ms/请求**、
   Python **37.8 ms/请求** ⇒ **比值 0.155（省 6.5×）**。
   差额来自两处：Rust 的边际处理便宜，**且它的空转也更低**（0.57% vs 0.90% 单核）。
3. **端到端吞吐基本不变**：C1 +2.7%、C2 +0.0%、C4 −3.6%、C5w −2.1%、C5n −6.7%；
   只有长 prompt 的两点略高（C3 +16.7%、I8k +8.5%，都是单轮 n=16，噪声大）。
   两侧共用同一个 NPU 引擎，引擎每请求吃 **≈840 ms CPU**，前端只吃 5–46 ms。
   ⇒ **换前端换不来吞吐，换来的是核预算**。
4. **前端占服务端 CPU 的比例**：Rust **1.1–6.0%**，Python **5.1–17.0%**。
   **C2（c=64）的 17.0% 是本项目「值得换」的最强证据**。
5. **延迟：短 prompt 上收益很小**（C1 TTFT −6.8 ms，只占前端 CPU 差额的 19%）；
   **长 prompt 上收益真实且大**（I8k TTFT **−82.8 ms**）。
6. **核数（前端可用 CPU 宽度）在本装置上不是瓶颈**：40 核 → 16 核，
   两侧前端成本变化都在 ±7% 以内（C5，§6）。

## 1. C1 · ISL=1k / OSL=128 / c=1（单流）

**负载**：`--random-input-len 1024 --random-output-len 128 --num-prompts 32 --max-concurrency 1`，
预热 4 个请求（不计入窗口）。两侧各跑 **3 轮**，每轮独立起停容器（新 KV cache、新编译缓存）。

### 1.1 原始 3 轮

| 轮次 | 侧 | 窗口 s | 前端 CPU s | 引擎 CPU s | 前端占服务端 | ms/请求 | TTFT ms | TPOT ms | req/s |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| r1 | Rust | 37.49 | **0.30** | 25.86 | 1.15% | 9.38 | 80.5 | 4.601 | 1.504 |
| r2 | Rust | 38.81 | **0.40** | 27.00 | 1.46% | 12.50 | 83.8 | 4.771 | 1.449 |
| r3 | Rust | 38.32 | **0.33** | 26.74 | 1.22% | 10.31 | 83.7 | 4.726 | 1.462 |
| r1 | Python | 38.45 | **1.47** | 27.04 | 5.16% | 45.94 | 88.9 | 4.770 | 1.439 |
| r2 | Python | 39.21 | **1.45** | 27.80 | 4.96% | 45.31 | 92.5 | 4.940 | 1.389 |
| r3 | Python | 38.98 | **1.48** | 27.33 | 5.14% | 46.25 | 90.5 | 4.819 | 1.423 |

### 1.2 中位数与比值

| 指标 | Rust | Python | **Rust / Python** |
|---|---:|---:|---:|
| 前端 CPU 秒（窗口内） | **0.33** | **1.47** | **0.2245** |
| 前端 CPU ms/请求 | **10.31** | **45.94** | **0.2245** |
| 前端 CPU s/千输入 token | 0.01048 | 0.04432 | 0.2366 |
| 前端 CPU s/千输出 token | 0.08057 | 0.35889 | 0.2245 |
| 引擎 CPU 秒 | 26.74 | 27.33 | 0.978 |
| 前端占服务端 CPU | **1.22%** | **5.14%** | — |
| 吞吐 req/s（端到端） | 1.462 | 1.423 | 1.027 |
| mean TTFT ms（端到端） | 83.7 | 90.5 | Δ **−6.8 ms** |
| mean TPOT ms（端到端） | 4.726 | 4.819 | 0.981 |

### 1.3 ⚠️ 口径警告：10.31 ms/请求 里含「空转」

C1 的窗口长 **38 s** 却只完成 **32 个请求**（1.4 req/s）。前端在整个窗口里都活着
（Rust 臂 tokio runtime + ZMQ io；Python 臂事件循环 + 2 个 ZMQ 线程），
它在等待引擎时被唤醒的开销**同样计入 `/proc/<pid>/stat`**。

⇒ 上表的 `ms/请求` 是**含空转**口径：`前端 CPU ÷ 完成请求数`。
**它不能直接用来算「单核能支撑多少 req/s」**——那必须用**边际成本**（§2）。
也不能与 x86 mock 臂的 µs/请求直接相比（那个窗口里跑了几千个请求，空转可忽略）。

### 1.4 重复性

Python 侧 3 轮极稳（1.45–1.48 s，**±1%**，几十~上百个 tick）。
Rust 侧离散明显（0.30–0.40 s）：`utime+stime` 以 **10 ms tick** 为粒度，
C1 的 Rust 前端全程只有 **30–40 个 tick** ⇒ 单次量化台阶就是 **0.01 s / 32 = 0.31 ms/请求**。

> **这本身就是一条结论**：在本装置上 Rust 前端已经**便宜到接近 `/proc` 的分辨极限**，
> 继续用小样本窗口测它意义不大，必须靠 §2 的两点法放大信号。

## 2. 边际成本：两点法（最重要的一节）

### 2.1 方法

同负载形态、同并发（c=1、ISL=1k/OSL=128），**只改请求数**：
M32（n=32，与 C1 同规格）与 M128（n=128）。两点解方程组

```
CPU_total = r × W  +  m × N         （W=窗口秒数，N=完成请求数）
```

得到 **空转速率 `r`** 与**边际每请求成本 `m`**。斜率法**不需要预先假设空转是多少**，
这是它比「均值法」强的地方。

| 臂 | 窗口 W (s) | 请求 N | 前端 CPU (s) | **空转 r** | **边际 m** |
|---|---:|---:|---:|---:|---:|
| Rust | 38.89 | 32 | 0.41 | **0.57%** 单核 | **5.86 ms/请求** |
| Rust | 106.63 | 128 | 1.36 | 同上 | 同上 |
| Python | 38.81 | 32 | 1.56 | **0.90%** 单核 | **37.83 ms/请求** |
| Python | 107.48 | 128 | 5.81 | 同上 | 同上 |

**边际比值 Rust/Python = 5.86 / 37.83 = `0.155`（Rust 省 6.5×）**
—— 比 §1 的含空转比值 `0.225` 更好，因为 **Rust 的空转也更低**。

### 2.2 不确定度（必须写清）

| 来源 | 量级 | 说明 |
|---|---|---|
| tick 量化 | ±0.10 ms/请求 | Rust 差值 `1.36−0.41 = 0.95 s` = 95 个 tick，摊到 96 个请求 |
| 轮间漂移 | **±1.5 ms/请求（±25%）** | C1 三轮的 Rust 前端在 0.30–0.40 s 间波动；若该漂移独立，M32/M128 的差值带 ±14 tick |
| 合计 | **Rust 5.86 ms/请求（±25%）** | Python 侧 ±2%（信号强得多） |

⇒ **`0.155` 这个比值的合理区间约 `0.12 – 0.20`**。方向与量级是稳的，
但不要把它当作三位有效数字用。

### 2.3 引擎的边际成本（证明「同引擎」）

| 臂 | 引擎边际 | 引擎空转 |
|---|---:|---:|
| Rust | **849 ms/请求** | ≈0（两点法解出负值，即引擎基本无空转） |
| Python | **839 ms/请求** | ≈0 |

两侧引擎边际成本相差 **1.2%**，直接支持「唯一变量是前端」这一设计前提。

> 引擎**不做 token 级拆分**：它的 CPU 几乎全是「随请求的算力」，用
> `(N, Tin, Tout)` 三参数分解会与 `N` 共线（`data/ab/a3/fit.json` 里引擎那一路的
> R² 因此为负值，属预期，**不是**拟合失败）。

### 2.4 token 级拆分（参考，未作为主结论）

把 `r` 固定为两点法值后，对前端的 `(每请求, 每输入 token, 每输出 token)` 做最小二乘
（`data/ab/a3/fit.json`）：

| 臂 | 每千输入 token | 每千输出 token | R² |
|---|---:|---:|---:|
| Rust | 1.532 ms（1532 ns/token） | 26.404 ms（26.4 µs/token） | **0.950** |
| Python | 6.104 ms（6104 ns/token） | 180.996 ms（181.0 µs/token） | 0.221 |

⚠️ **Rust 侧拟合良好（R²=0.95），Python 侧一般（R²=0.22）**——后者说明前端成本
对 ISL/OSL 并非纯线性（也说明「固定空转速率」这个假设对 Python 侧更勉强）。
⇒ 表中 Rust 的 ns/token 级数字可作参考；**Python 侧不要引用**，改用 §5 的两点斜率。

## 3. C2 · ISL=1k / OSL=128 / c=64（并发）★ 最强证据

> ⚠️ 建容器时必须 `MAX_NUM_SEQS=64`（默认 8 会拒绝排队）；已固化在
> `harness/a3/matrix.sh` 的 `CONFIG_TABLE`。

| 指标 | Rust | Python | Rust/Python |
|---|---:|---:|---:|
| 前端 CPU 秒 | **1.24** | **3.93** | **0.316** |
| 前端 CPU ms/请求 | **4.84** | **15.35** | **0.316** |
| s/千输入 token | 0.00488 | 0.01481 | 0.329 |
| s/千输出 token | 0.03784 | 0.11993 | 0.316 |
| 引擎 CPU 秒 | 19.37 | 19.15 | 1.012 |
| **前端占服务端 CPU** | **6.01%** | **17.03%** | — |
| 吞吐 req/s | 15.458 | 15.463 | **1.000** |
| mean TTFT ms | 649.8 | 690.9 | **Δ −41.0 ms** |
| mean TPOT ms | 27.214 | 26.893 | 1.012 |

**为什么这是「值得换」的最强证据**：c=64 时 Python 前端吃掉服务端 CPU 的 **17%**，
Rust 只有 **6%**。同样 15.5 req/s 的吞吐下，换前端能**省下 11 个百分点的服务端 CPU**——
这是本装置上唯一「前端成本占比达到两位数量级」的负载点。

**同时注意**：吞吐仍然**几乎完全一样**（15.458 vs 15.463）。c=64 时引擎
（TPOT 27 ms/token）是瓶颈，前端省下的 CPU 没有变成吞吐，
而是变成了**为引擎留出的 CPU 余量**。

## 4. C3 / I8k · 长 prompt

C3（ISL=8k/OSL=16）与 I8k（ISL=8k/OSL=128）都要求 `MAX_MODEL_LEN=16384`
（默认 4096 会拒绝）。

### 4.1 C3 · ISL=8k / OSL=16 / c=1

| 指标 | Rust | Python | Rust/Python |
|---|---:|---:|---:|
| 前端 CPU 秒 | 0.32 | 0.87 | **0.368** |
| 前端 CPU ms/请求 | **20.00** | **54.38** | 0.368 |
| s/千输入 token | 0.00257 | 0.00663 | 0.388 |
| s/千输出 token | 1.25000 | 3.39844 | 0.368 |
| 引擎 CPU 秒 | 8.39 | 9.25 | 0.907 |
| 前端占服务端 CPU | 3.67% | 8.60% | — |
| 吞吐 req/s | 2.357 | 2.019 | **1.167** |
| mean TTFT ms | **353.4** | **430.5** | **Δ −77.1 ms** |
| mean TPOT ms | 4.707 | 4.303 | 1.094 |

### 4.2 I8k · ISL=8k / OSL=128 / c=1（受控点）

固定 `OSL=128`（与 C1 相同），**只把 ISL 从 1k 拉到 8k**：

| 指标 | Rust | Python | Rust/Python |
|---|---:|---:|---:|
| 前端 CPU 秒 | 0.43 | 1.37 | **0.314** |
| 前端 CPU ms/请求 | **26.88** | **85.63** | 0.314 |
| s/千输入 token | 0.00345 | 0.01044 | 0.331 |
| s/千输出 token | 0.20996 | 0.66895 | 0.314 |
| 引擎 CPU 秒 | 18.39 | 19.65 | 0.936 |
| 前端占服务端 CPU | 2.29% | 6.52% | — |
| 吞吐 req/s | 1.063 | 0.980 | **1.085** |
| mean TTFT ms | **341.2** | **424.0** | **Δ −82.8 ms** |
| mean TPOT ms | 4.720 | 4.698 | 1.005 |

### 4.3 长 prompt 的结论

1. **TTFT 收益是真实的、且量级最大**：I8k 的 **−82.8 ms** 与 C3 的 **−77.1 ms** 一致。
   机制清楚：8k token 的模板渲染 + 分词 + 序列化**在 prefill 之前、与引擎串联**，
   所以省下的前端时间**直接体现为 TTFT**。对比 C1（ISL=1k）只有 −6.8 ms。
2. **吞吐开始出现可见差异**：C3 **+16.7%**、I8k **+8.5%**（单轮，n=16，噪声较大）。
3. ⚠️ **但前端 CPU 的比值反而变差**（C1 0.225 → I8k 0.314 → C3 0.368）。
   方向与 `docs/05` 的分段预测（P2 的 Rust/Python 优势随 ISL 从 0.56 拉大到 0.36）相反。
   受控点 I8k 排除了「两轴同时动」这个解释 ⇒ **在真实引擎装置上，长 prompt 反而削弱
   Rust 的相对优势**。最可能的原因：长 prompt 时前端**等引擎 prefill 的时间更长**
   （I8k 的 TTFT 341 ms），唤醒/轮询类开销按时间累积，而 Python 侧这部分开销的
   **增长斜率更平**（其绝对量大，固定项占比高）。**这条标注为「有受控证据、机制待验」**。

## 5. C4 · ISL=1k / OSL=512 / c=1（长输出）

| 指标 | Rust | Python | Rust/Python |
|---|---:|---:|---:|
| 前端 CPU 秒 | 0.59 | 2.63 | **0.224** |
| 前端 CPU ms/请求 | **36.88** | **164.38** | **0.224** |
| s/千输入 token | 0.03750 | 0.15860 | 0.236 |
| s/千输出 token | 0.07202 | 0.32105 | 0.224 |
| 引擎 CPU 秒 | 51.06 | 49.15 | 1.039 |
| 前端占服务端 CPU | 1.14% | 5.08% | — |
| 吞吐 req/s | 0.381 | 0.395 | 0.965 |
| mean TTFT ms | 84.5 | 90.7 | Δ −6.2 ms |
| mean TPOT ms | 4.968 | 4.775 | 1.040 |

**OSL 斜率**（ISL 固定 1k、c=1，扣掉 §2 的空转后）：

| 点 | OSL | Rust 扣空转 ms/请求 | Python 扣空转 ms/请求 |
|---|---:|---:|---:|
| S16 | 16 | 1.85 | 9.06 |
| C1 | 128 | 3.46（3 轮中位） | 35.12（3 轮中位） |
| C4 | 512 | 16.08 | 132.49 |

⇒ **每输出 token 的边际前端成本**：Rust **≈28.7 µs/token**、
Python **≈248.9 µs/token**（两点法，`(C4−S16)/496`），**比值 0.115**。
⚠️ 该斜率假设「空转速率与 OSL 无关」，而这**不一定成立**（OSL 越长、引擎产出越频繁、
前端被唤醒越多）⇒ 标【推断】。

**延迟小结**：OSL=512 时 TTFT 只差 6.2 ms、TPOT 反而 Python 略快（+4%），
**长输出场景换前端几乎不影响延迟**——因为 decode 期前端与引擎并行。

## 6. C5 · 核数扫描（前端可用 CPU 拓扑宽度）

⚠️ **口径**：NPU 装置上「核数」指的是**给服务容器（含前端与引擎进程）的 cpuset 宽度**，
不是 NPU 算力。客户端固定绑在 200-201，两侧完全一致。

| 点 | cpuset | 宽度 | Rust ms/请求 | Python ms/请求 | 比值 | Rust req/s | Python req/s |
|---|---|---:|---:|---:|---:|---:|---:|
| C5w | 160-199 | 40 核 | **6.875** | **19.688** | 0.349 | 7.014 | 7.168 |
| C5n | 160-175 | 16 核 | **7.344** | **20.156** | 0.364 | 6.752 | 7.234 |

**结论：核数基本不重要。**

- 40 核 → 16 核（砍掉 60%），Rust 前端成本 +6.8%、Python +2.4%，
  吞吐变化 −3.7% / +0.9% —— **都在单轮噪声量级内**。
- 原因是**前端远没有吃满核**：C2（15.5 req/s）时 Rust 前端只占 **0.35 个核**、
  Python 占 **1.13 个核**；C5（7 req/s）时只有 0.17 / 0.49 个核。
- ⇒ 在「引擎在 NPU 上」的装置里，**前端可用 CPU 宽度不是约束**；
  Q4 的拐点不在核数轴上（详见 `docs/06`）。

## 7. 前端成本占服务端 CPU 汇总（`docs/06` 的输入）

| 点 | 负载 | Rust | Python | 倍数 |
|---|---|---:|---:|---:|
| C1 | 1k/128/c=1 | **1.22%** | **5.14%** | 4.2× |
| C2 | 1k/128/c=64 | **6.01%** | **17.03%** | 2.8× |
| C3 | 8k/16/c=1 | 3.67% | 8.60% | 2.3× |
| C4 | 1k/512/c=1 | 1.14% | 5.08% | 4.5× |
| C5w | 1k/128/c=8 | 3.74% | 10.34% | 2.8× |
| C5n | 同 C5w，16 核 | 3.83% | 10.71% | 2.8× |
| I8k | 8k/128/c=1 | 2.29% | 6.52% | 2.8× |

> 分母 = 容器内**全部进程**的 CPU 秒（前端 + 引擎 + 其它）。
> ⚠️ 由于引擎跑在 NPU 上，这个「服务端 CPU」主要是引擎在 host 侧的调度/同步开销；
> 它衡量的是「前端在服务端 CPU 账单里占多大份额」，不是「前端占端到端时间」。

### 7.1 前端 CPU 差额有多少落到端到端延迟上

以 C1（3 轮中位）为例：

| 项 | Rust | Python | 差 |
|---|---:|---:|---:|
| 前端 CPU（含空转） | 10.31 ms | 45.94 ms | **35.63 ms** |
| 其中体现在 TTFT（首 token 前，串联） | 83.7 ms | 90.5 ms | **6.80 ms** |
| 其中体现在 TPOT（decode 期，与引擎并行） | 4.726 ms/tok | 4.819 ms/tok | ×128 = 12.03 ms |
| **落回关键路径合计** | — | — | **18.83 ms（53%）** |

⇒ **前端 CPU 的差额只有约一半变成端到端延迟的差额，另一半与引擎并行**。
这解释了「CPU 差 35.6 ms，但 TTFT 只差 6.8 ms」这个乍看矛盾的现象，
也是 Q3 的准确答案：**换前端的收益主要在 CPU/容量，不在延迟**。

⚠️ 上表把「TTFT 差」与「TPOT×OSL 差」直接相加是**近似**：TTFT 里还含 prefill
与排队，并非全是前端；标【推断】。**未做**前端内部埋点，无法精确分离（见 §9）。

## 附录 A · x86 纯 CPU 装置（**不可与主结论混用**）

装置：本机 `LOCAL_HOST`（x86_64，12 核），vLLM **0.26.0+cpu** wheel
（构建 commit 同为 `568afb3a`），纯 CPU forward，**TPOT 245 ms/token**。

### A.1 真引擎臂（`data/ab/C1/`，引擎是瓶颈）

| 角色 | 前端 CPU s | ms/请求 | s/千输入 tok | s/千输出 tok |
|---|---:|---:|---:|---:|
| Rust（`vllm-rs`） | 0.23 | 57.5 | 0.0562 | 0.449 |
| Python（API server） | 0.61 | 152.5 | 0.1489 | 1.191 |
| 引擎（`VLLM::EngineCore`） | 25.32 | 6 330 | 6.18 | 49.45 |
| Worker | 246.90 | 61 725 | 60.28 | 482.23 |

**前端占服务端 CPU：0.08%（Rust）/ 0.22%（Python）** ⇒ 该装置上 A/B 差异
**被引擎淹没**，只能证伪、不能回答 Q3/Q4。这正是迁移到 REMOTE_HOST 的原因。

### A.2 mock 引擎臂（`data/ab/*-mock/`，前端受限）

引擎换成 `vllm-mock-engine`（≈免费，**不占 NPU**）后，前端占服务端 CPU ≈100%，
测的是**前端差距的上界**。请求数取 512–8192（mock 引擎不成为瓶颈），
前端 CPU 远离 tick 分辨率：

| 点 | 负载 | Rust ms/请求 | Python ms/请求 | **比值 R/P** |
|---|---|---:|---:|---:|
| C1-mock | ISL=1k/OSL=128/c=1 | **4.01** | **10.39** | **0.386** |
| C2-mock | 同 C1/c=64 | **1.318** | **8.861** | **0.149** |
| C3-mock | ISL=8k/OSL=16/c=1 | **5.352** | **24.746** | **0.216** |
| C4-mock | ISL=1k/OSL=512/c=1 | **7.773** | **24.736** | **0.314** |
| C5a-mock | ISL=1k/OSL=128/c=8 | **1.760** | **10.493** | **0.168** |

**方向与主结论一致**（Rust 0.15–0.39×），且 c=64 时 Rust **快 6.7×**——
与 REMOTE_HOST 真引擎臂的 C2（0.316）在同一量级。
⇒ 两个**互相独立**的装置（x86 纯 CPU + mock 引擎 / REMOTE_HOST NPU + 真引擎）
给出同向结论，提高了主结论的稳健性。

> ⚠️ 但仍**不可与主结论相除**：mock 臂的「Python 前端」用的是
> `vllm serve --api-server-count 1 --data-parallel-size-local 0`
> 这个**特制配置**（等外部 mock engine 注册，见 `harness/ab/start_mock_side.sh`），
> 与真引擎臂的拓扑 A（主进程即 API server 并自拉引擎）不同；
> 且 mock engine 的 tick 极密、前端能批量摊销，与真引擎「每 tick 一个 token」
> 的唤醒模式完全不同。**只能用来做方向性交叉验证。**

### A.2b x86 上的「空转」直接实测

同一台机器上让 Rust 前端栈**空转 60 秒**（不发任何请求）：
`vllm-rs` 的 CPU 增量为 **0.00 s**（低于 10 ms tick 分辨率），engine core 也是 0.00 s，
只有 Worker 有 0.33 s。
⇒ **x86 装置的 `vllm-rs` 确实没有可测的空转**，与 REMOTE_HOST 上两点法解出的
0.57% 单核不同 —— 因为 REMOTE_HOST 上真引擎每 4.8 ms 产一个 token，前端被**频繁唤醒**。
这条差异也解释了为什么「含空转的每请求 CPU」在两个装置上不可直接比较。

### A.4 为什么附录不能与 §1–§8 混用

| 维度 | x86 附录 | REMOTE_HOST 主结论 |
|---|---|---|
| 架构 | x86_64 | aarch64（Kunpeng 920B） |
| 引擎 | 纯 CPU forward | Ascend 910 |
| 引擎速度 | 245 ms/token | ≈4.8 ms/token |
| 前端占服务端 | 0.08% | 1.2% / 5.1% |

⇒ **跨装置相除无意义**（既跨架构又跨加速器）。附录只用来展示「装置分辨率」这一方法论点。
